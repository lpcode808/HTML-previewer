Prompt kit

Prompts that turn an HTML app into something to learn from. They work with whatever AI you use (Gemini, ChatGPT, Claude, and others).

  1. Copy a prompt.
  2. Paste it into your AI, then paste the app's whole HTML file underneath it.
  3. Check the answer before handing it out. The tips under each prompt say what to look for.

Learning guide experimental

A one-page guide to one app: what each part does, the real line of code behind it, and "predict, then try" tasks that have the student change a value and guess what happens first.

  • You get: a single HTML file. Paste it into the Playground, read it there, then use Download to hand it out.
  • Check: search the app for each quoted line (Ctrl+F or ⌘F). If one isn't there, the AI made it up. Fix it or delete it.
  • Answers: the AI lists what should happen for each "predict, then try" after the HTML, in its chat reply, so the answers aren't in the hand-out.
Read the prompt 
You are writing a one-page learning guide about an app a student made with AI. The student did not write the code line by line. The goal is for them to understand their own app well enough to explain it and change it.

Do NOT rewrite, fix, or reprint the app.

Make the guide one complete HTML file, with its CSS inside it and no links to other files. It should be easy to read on a laptop and print cleanly.

Include these sections, in this order:

1. What makes this app different. One or two sentences about what this app does that other apps like it don't. Start with that.

2. The parts. Pick 3 to 6 parts of the app: things you can see on screen, and what happens behind them. For each part:
   - One or two plain sentences about what it does.
   - The line of code that does it, copied EXACTLY from the file, character for character, in a code box. Never make up, shorten, or tidy a quote. If you are not sure of the exact text, leave the quote out.
   - "Predict, then try": name one value on that line and what to change it to. Ask the student to write down what they think will happen BEFORE they try it. Do not say what will happen.

3. Look closely. If something in the code looks odd, unused, or might not do what it seems to, point to it as a question, not an answer. If nothing does, leave this section out.

4. Big ideas. For each of these, point to one place in the code, with one sentence and the quoted line: decomposition (breaking a problem into parts), pattern (something that repeats), abstraction (a name that hides details), algorithm (steps in order).

5. Explain it out loud. Three questions the student could answer in a one-minute talk about their app.

Writing rules: talk to the student ("your app"). Use plain words and short sentences. Explain any code word the first time you use it. Never say "just", "simply", or "easy".

After the HTML file, OUTSIDE it, write a short list for the teacher: for each "predict, then try", what should happen.

Tinker knobs experimental

Sliders, color pickers and text boxes that each change one value on one real line of the app, with that line shown as it changes. See an example.

  • You get: a short knob list. Paste it with the app into the tinker page, or bake one file to hand out with tinker/build.py (see the tinker README).
  • Check: knobs whose code isn't in the app turn red and are skipped. The app still runs. A few red knobs are fine. Mostly red means try another AI.
Read the prompt 
You are helping a student tinker with an app they made. Do NOT rewrite, fix, or reprint the app.
Your only job is to find 5 to 8 "knobs": single values in the code that the student can change and SEE
change right away (colors, sizes, speeds, counts, words on screen).

Rules for every knob:
1. "code" is a short piece of text copied EXACTLY, character for character, from ONE line of the
   file. It must appear only ONCE in the whole file. Use the shortest piece that is still unique.
2. "value" is the exact part of "code" that will change. It must appear inside "code".
3. Two knobs must never change the same characters.
4. "type" is "number", "color" (only 6-digit hex like #1e40af), or "text".
5. For numbers, give "min", "max", and "step" that keep the app working but let the student push it.
6. "label" is 2 to 5 plain words the student would use ("Home end zone color", not "fillStyle").
7. "why" is one sentence, under 25 words, saying what this value controls. If changing it has
   a surprise (something else does NOT change with it), say so. Never say "just" or "easy".
8. Put first the knobs for what makes THIS app different from every other app like it.

Answer with ONLY this JSON, no other words:
{
  "app": "name of the app",
  "knobs": [
    { "label": "", "code": "", "value": "", "type": "number", "min": 0, "max": 0, "step": 1, "why": "" }
  ]
}
